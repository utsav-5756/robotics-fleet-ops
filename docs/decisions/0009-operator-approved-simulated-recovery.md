# ADR 0009: Operator-approved simulated reconnect

## Status

Accepted and implemented. Unit and API integration tests cover approval, rejection, idempotency, simulator outcomes, and incident resolution.

## Context

The project needs a visible recovery workflow that demonstrates operator authority without connecting to physical robots or exposing motor controls. The existing simulator makes connectivity incidents reproducible, and the dashboard already presents incident evidence.

## Decision

Implement one allowlisted action: SIMULATED_RECONNECT, available only for an active ROBOT_DISCONNECTED incident. The action is selected by fixed backend logic and is not generated by the investigation agent.

The operator first generates and reviews an evidence-backed investigation report. The dashboard then creates a pending request linked in the audit event to that report, its fixed recommendation, and supporting evidence IDs. A request without a saved report is rejected. Creating a pending request does not contact the simulator. An operator must review the evidence, check an explicit approval statement, and choose Approve simulated reconnect. Rejection is recorded without changing simulator state.

After approval, the backend sends the fixed action to an internal simulator HTTP endpoint on the Docker Compose network. The endpoint is not published to the host. It validates the action type, run ID, and fault-target robot, then changes only the simulated connectivity state. The simulator's next telemetry sample reports the robot connected, allowing the existing deterministic incident lifecycle to resolve the incident.

A SQLite recovery-request record holds current state. Separate append-only audit events record the incident and linked recommendation, decision, and execution outcome. Requests are single-decision; an approved request is not replayed. If the simulator does not confirm, the request is marked failed and the outcome warns the operator to inspect current simulated state.

## Safety and limitations

- The investigation model has no recovery tools and cannot approve or select executable actions.
- The action changes simulation state only and sends no motor command.
- A request must reference an active disconnection incident; the incident is checked again at approval time.
- The action service is reachable only over the internal Compose network and is not exposed on a host port.
- The local demo has no login. The operator label is self-reported and does not authenticate a person.
- A simulator timeout may leave the outcome unconfirmed. The request is not replayed automatically; inspect current telemetry.
- This workflow is a portfolio demonstration, not production authorization or robot-safety control.
